## O que multiplica não é o proxy do WARP

O cliente Cloudflare WARP no Windows é um serviço global: **um** registro, **um** túnel, **uma** porta de proxy (`127.0.0.1:40000`). Não existe `warp-svc` instância 2. Multiplicar portas do WARP não multiplica saída — todas saem pelo mesmo device.

O que multiplica é **identidade WARP materializada como WireGuard userspace**. Cada `wgcf register` gera um device novo com chaves próprias; cada device vira um `wireproxy.exe` independente, escutando na própria porta, sem driver, sem admin, sem tocar na tabela de rotas. Isso já está no launcher — modo `WIREGUARD` (v2.37) roda `.conf` por wireproxy 1.1.3 pinado por SHA-256. Só que hoje é **serial**: `$Port = 25345` fixo, um `wireproxy.pid`, um `run.conf`, "um .conf depois do outro". O que falta é transformar isso em pool concorrente.

E o isolamento não vem do proxy — vem do ambiente do processo. `HTTPS_PROXY` só afeta a árvore que o recebeu. Quem não recebe, sai direto. Isso é o que permite N instâncias com N IPs, e é também o que exige verificação por instância.

## O que já existe e o que atrapalha

| Peça | Estado real |
|---|---|
| `MULTI_INSTANCE=1` | existe, isola `STATE_DIR` em `instances\<SID>` — mas **não isola egress** |
| `multi-dispatcher.ps1` + `queue-add.ps1` | prontos, `MULTI=0`, nunca ligados |
| `warp-rotate.ps1` + `warp-rotate.lock` | rotação **global serializada** entre workers — é exatamente o que o pool elimina |
| wireproxy | baixado e verificado, mas 1 túnel por vez |
| OpenCode v2 | serviço de background compartilhado; sem `--standalone` + XDG separado, N CLIs falam com **o mesmo** servidor nascido com **um** proxy |
| Desktop | Electron, `requestSingleInstanceLock()`, um sidecar com `proxyEnv()` global |

Dois detalhes que definem o desenho: o Bun do OpenCode fala **HTTP proxy, não SOCKS5** (o launcher já tem bridge HTTP→SOCKS por isso), então cada slot tem que expor `[http]`. E o `serviceEnv()` do desktop injeta proxy só no sidecar — o renderer Electron usa proxy do sistema, não env.

## Arquitetura proposta

**Pool de slots**, cada slot uma unidade autônoma:

```
instances\egress\slot01\  account.toml + profile.conf + run.conf + slot.json
                          wireproxy.exe -c run.conf  →  127.0.0.1:42001  [http]
slot.json: { slot, port, pid, startTime, ip, colo, warp, created, burned[] }
```

- **Criação de identidade**: `wgcf` pinado por SHA como o wireproxy já é. `register --accept-tos` + `generate` → `.conf` por slot. `WG_DIR` manual continua como fonte alternativa.
- **Portas**: base 42000 + índice. Abaixo de 49152, fora do bloco que o Windows reserva para conexões de saída.
- **Sem lock global**: cada slot tem lock próprio. Instância 03 bate limite → rotaciona só o slot 03, as outras 7 continuam.
- **Colisão de IP**: no start e a cada health check, `cdn-cgi/trace` por porta. Dois slots com o mesmo `ip=` → o mais novo re-registra. IPs do WARP free saem do pool do colo, colisão é esperada, não é bug.
- **Rotação em dois níveis**: reconnect da mesma identidade primeiro (barato, quase sempre muda IP); re-register só se repetir IP ou `warp=off`.
- **Health loop**: processo morto, `warp=off`, IP mudou sozinho → slot marcado unhealthy e reconstruído isoladamente.

**Isolamento por instância** — cinco camadas, todas já possíveis com o que o binário expõe:

| Camada | Mecanismo |
|---|---|
| Rede | `HTTPS_PROXY=http://127.0.0.1:420NN` + `NO_PROXY=127.0.0.1,localhost,::1` |
| Serviço | `--standalone` por worker (servidor próprio, nasce com o proxy certo) |
| Estado | `XDG_DATA_HOME` / `XDG_STATE_HOME` / `XDG_CONFIG_HOME` por instância (o `global-roots.ts` lê exatamente essas) |
| Porta | service port fixado por instância no `service.json` |
| Identidade de app | `LOCALAPPDATA`/`APPDATA`/`USERPROFILE` por worker — o `device-reset.ps1` já faz |

## Limites que mudam o escopo

1. **WARP client tem que estar desconectado** durante o pool. Em modo túnel ele captura o UDP do wireproxy e todas as instâncias voltam ao mesmo IP. Modo proxy do WARP não conflita, mas é redundante.
2. **Desktop: uma instância por máquina.** O lock é do app. Para N janelas com N IPs seria preciso patch no `configure.ts` + `--profile` por userData — e ainda assim só o tráfego do sidecar é isolado, não o do renderer.
3. **N real é modesto.** Cada wireproxy ~20–30 MB; 8–12 slots é confortável. Quantos registros anônimos o Cloudflare aceita por IP antes de limitar é algo a **medir**, não assumir — começo com 4 e subo observando falha de registro.

### `up`

1. Recusa rodar se `warp-cli status` reportar `Connected` (modo túnel captura o UDP do wireproxy e colapsa tudo num IP só).
2. Para cada slot: identidade existe? senão `wgcf register` + `generate`. `WG_DIR` vence se houver `slotNN.conf` — é o override que combinamos.
3. Valida a porta `POOL_PORT_BASE + slot` livre. Se ocupada, **falha o slot**, não desloca — a instância já está pinada nela.
4. `wireproxy -s -c run.conf`, grava `pid|startTime` (mesmo padrão do `Proxy-Pid`, linha 10006, para nunca matar PID reciclado).
5. Trace por porta. `warp=on`, IP não vazio, IP fora do `burned[]`.
6. **Dedupe**: agrupa por IP, mantém o menor índice, rotaciona os demais com `-Force` (identidade nova) até `POOL_DEDUPE_TRIES`. Se persistir, slot fica `degraded` — proxy sobe, mas o `claim` não entrega ele.
7. Grava `pool-status.json` com a tabela final.

### `rotate` — dois níveis

- **reconnect** (padrão): mata e sobe o mesmo `run.conf`. Nova sessão WireGuard, IP novo em 2–4s, sem tocar em identidade. Custo zero de registro.
- **identity** (`-Force`): `wgcf register` novo device, `generate`, reescreve `run.conf`, sobe.

Regra: reconnect primeiro; se o IP voltar igual duas vezes ou já estiver em `burned[]`, escala para identity. `burned[]` com TTL de 24h, igual ao `BURNED_FORGET_MS` do desktop.

### `claim` — atribuição atômica

Trava `instances\egress\slotNN.lock` com `FileShare::None`, lê `slot.json`, confere `health=up`, grava o dono (`SID`, `pid`, `ticks`) e escreve `instances\<SID>\egress.json`:

```json
{ "slot": 2, "port": 42002, "proxy": "http://127.0.0.1:42002", "ip": "104.28.x.x" }
```

`claim` é idempotente: mesma instância pedindo de novo recebe o mesmo slot. `reap` libera slot cujo dono morreu e cujo `lastCheck` passou de `POOL_LEASE_MIN`.

### `daemon`

Loop de `POOL_HEALTH_SEC` (30s): processo vivo, porta aceitando, trace respondendo. Morto ou `warp=off` → reconstrói só aquele slot. Eventos em `recovery-events.jsonl`: `pool_up`, `pool_slot_up`, `pool_rotate`, `pool_degraded`, `pool_collision`, `pool_reaped`.

## No uso real

**1. Quatro conversas avançando ao mesmo tempo, não uma.**
Hoje o limite grátis para tudo, gira o IP global, e só então uma retoma. Com o pool, cada worker bate o teto no seu próprio relógio e gira sozinho. A fila drena em paralelo em vez de em fila indiana.

**2. Rotação deixa de ser evento global.**
O `warp-rotate.lock` some. Um worker bate limite, o slot dele troca de IP em 2–4 segundos, e as outras três instâncias não percebem. Hoje toda rotação é um soluço para todo mundo, inclusive o Desktop.

**4. A fila vira máquina de verdade.**
`multi-dispatcher.ps1` está pronto mas manda worker sem proxy nenhum — eles rodam no IP da casa. Com o pool, cada item da fila sai por um IP diferente. É a diferença entre "script que paraleliza processos" e "script que paraleliza capacidade".

`burned[]` com TTL de 24h por slot. O pool não devolve ao mesmo worker um IP que ele já gastou. Hoje isso é um `lastip.txt` global que não sabe quem usou o quê.

Não é só IP: cada worker já tem `LOCALAPPDATA`/`USERPROFILE` próprios, ou seja, device fingerprint e sessão separados. IP distinto + identidade distinta é mais do que IP distinto.

`pool-status.json` com slot, porta, IP, colo e saúde. `instances\instNN\egress.json` diz exatamente por onde aquele worker saiu. Hoje o IP só aparece em log e você descobre o resto por inferência.

## O limite honesto

Isso multiplica **IPs simultâneos**, não a cota. A premissa do projeto inteiro é que o limite é por IP — o launcher já existe justamente porque girar IP destrava. Se em algum momento o limite virar por conta, o pool não ajuda em nada. Vale confirmar isso na Fase 0 junto com a medição dos IPs.

E o teto prático não é 12. É RAM e qualidade do UDP da sua operadora: 4 slots é confortável, 8 é possível, 12 é experimento. O número sai da medição, não da ambição.

Resumindo o que muda no dia: hoje você tem **uma** conversa acelerada por rotação. Depois tem **quatro** correndo lado a lado, cada uma no seu IP, com o Desktop intocado em cima — e um arquivo de estado que te diz exatamente o que está acontecendo.
